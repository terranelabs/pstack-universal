### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or plan, deliver it and stop. Execution starts only on the operator's explicit go. Record the program objective in the host's durable goal or task mechanism when one exists; otherwise keep it in `decisions.tsv` and the current task.
2. **Launch one owner per PR with the full lifecycle and an early trail.** Read **pstack-runtime** and require explicit authorization for branch pushes, PR creation, and merging. Resolve the forge once for the program. GitHub CLI (`gh`) is the default; use Origin when installed and able to resolve the repository. One isolated host-native owner per PR handles build, first push, ready PR, self-proof on the real artifact, skeptical bot-comment triage, diff cleanup, `/no-comments`, a rebase onto current trunk, the babysit loop, and, only when explicitly authorized, the merge. Every owner starts a `decisions.tsv` trail early. Keep it uncommitted unless the user authorized committing it. The merge is the one step an owner may not take alone; step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Swarm-verify every merge-ready head before its merge.** At the owner's merge-ready head SHA, fan out independent verifiers per **swarm** and aggregate one verdict. Re-run the gates, prove load-bearing behavior on the real surface with host-native tools, and audit receipts and diff while distrusting the PR body. Run the same load-bearing scenario on trunk where meaningful. No merge without the root's clean verdict. If independent delegation is unavailable, stop at merge-ready because the gate cannot be satisfied.
5. **On a clean verdict, merge only under explicit authority.** The owner merges only from a head freshly rebased onto trunk and only when the user's request explicitly grants merge authority. The swarm verdict pins the head SHA. If trunk moves, apply the patch-id re-verification rule from `shipping.md`. Operator-named items always stop at merge-ready and wait for the operator.
6. **Run the root layer.** A new raise of a pinned gate or budget value needs a fresh countersign after verifier proof. Run an audit tick roughly every 30 minutes with the host's native wait, heartbeat, or scheduler. If none exists, record the continuation needed. At each tick, re-read this playbook and the stored objective, probe owners through host-native status operations, and collect decision trails. Count only observable side effects as progress. Replace stuck owners when the host supports interruption and redispatch.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
